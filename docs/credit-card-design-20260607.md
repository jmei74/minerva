## 一、背景

### 1.1 市场洞察

新加坡主流信用卡（DBS Live Fresh、UOB EVOL、OCBC 365）的返现机制有三个共同特征：

1. **分段返现**：不同消费类别（餐饮、网购、交通）适用不同返现比例
2. **月低保门槛**：需单月消费满 S$600-800 才触发返现（DBS Live Fresh S$800/月，OCBC 365 S$600/月）
3. **类别上限**：每类消费返现有独立上限（如 Citi Cashback 每类 S$25/月）

### 1.2 用户痛点

当前信用卡 App 普遍存在以下问题：
- **信息不透明**：用户消费后才知道有没有返现，无法提前规划消费节奏
- **门槛进度不清晰**：距离低保门槛还差多少？本月还剩多少额度？
- **除外类目干扰**：用户以为"保险缴费能返现"，实际被排除在规则外，导致投诉

### 1.3 设计目标

参考 UOB EVOL（10% 返现）、DBS Live Fresh（6% 返现）等成熟产品的规则，设计一个**智能分段返现引擎**，作为信用卡 App 的核心功能模块。

## 二、功能描述

### 2.1 核心功能矩阵

| 功能 | 描述 | 用户价值 |
|------|------|---------|
| **F1. 实时返现预估** | 消费完成后3 秒内展示该笔交易的预估返现金额与类别 | 消除"不知道能返多少"的不确定感 |
| **F2. 月度进度追踪** | 实时展示：距低保门槛差额、各类别已用/剩余返现额度 | 帮助用户主动规划消费，触发返现 |
| **F3. 除外类目提醒** | 交易被归类为除外类目时，主动推送"该交易不参与返现"提示 | 减少用户误解与客诉 |
| **F4. 多卡切换对比** | 支持绑定多张信用卡，切换后展示该卡当前返现状态 | 辅助用户决策"用哪张卡" |
| **F5. 返现历史报表** | 按月/按类别汇总返现金额，支持导出 CSV | 数据透明，增强用户信任 |

### 2.2 用户场景示例

**场景：小明，月薪 S$5,000，持有一张 DBS Live Fresh Card（6% 返现，门槛 S$800/月）**

- 6月10日，小明用信用卡买了咖啡 S$6 → App 即时展示「+S$0.36返现」
- 6月20日，小明消费了 S$750，还差 S$50 触发本月门槛 → App 推送「本月再消费 S$50，即可解锁6% 返现」
- 6月21日，小明交保险费 S$1,000 → App 推送「保险缴费不参与返现，不计入门槛」
- 6月30日，本月返现共 S$12.50 → App 推送月度返现报告

### 2.3 差异化设计亮点

1. **Pre-transaction 提示（创新点）**：用户在付款前查询"某商户/某类消费能返多少"，这是新加坡现有产品均未提供的功能，可作为核心差异化卖点
2. **储蓄账户联动**：结合 DBS Multiplier 的高利率储蓄账户联动逻辑，展示"消费达标 → 储蓄利率提升"的综合收益
3. **SimplyGo 交通自动计入**：参考 DBS Live Fresh 将公共交通 SimplyGo 纳入返现范围和门槛计算

### 3.2 关键模块说明

####3.2.1 返现规则引擎

- **输入**：交易记录（金额、商户MCC码、时间、卡号）
- **处理逻辑**：
  1. MCC码 → 消费类别映射（如5812=餐饮，5411=超市）
  2. 根据卡种规则（从规则配置后台读取），匹配返现比例
  3. 检查是否属于除外类目（保险/政府缴费/教育等）
  4. 计算返现金额（含分段上限逻辑）
- **输出**：返现金额、类别、剩余额度

#### 3.2.2 除外类目过滤器

参考 Elaine 研究中的 UOB EVOL 除外规则：
- 保险缴费（政府类 MCC）
- 政府缴费（水电费、税务等）
- 教育类（学费、学校缴费等）
- 投资理财类（转账、理财购买等）

#### 3.2.3 卡组织交易分类对接

| 卡组织 | 交易分类接口 | 说明 |
|--------|------------|------|
| Visa | Visa IntelliServer / VFPS | 商户类别码（MCC）实时分类 |
| Mastercard | Mastercard SpendingPulse | 消费数据分析 |
| AMEX | American Express Open | 卡产品特定分类规则 |

### 3.3 数据模型

```

MonthlyProgress {
  card_id: string

    remaining_cap: decimal
  }]
}
```

- **规则引擎配置化**：避免硬编码，通过配置后台管理规则，降低后期维护成本

## 六、风险提示

| 风险 | 级别 | 缓解措施 |
|------|------|---------|
| **MCC 码映射不准确**（商户分类错误导致返现金额错误） | 🟡 中 | 引入第三方商户分类数据（如 Swiviel/客乐芙），建立人工审核流程 |
| **规则配置错误**（设置错误的返现比例/上限） | 🔴 高 | 上线前双人审核规则配置，建立灰度发布机制 |
| **卡组织 API 对接延迟**（Phase 3 依赖卡组织接口） | 🟡 中 | MVP 阶段使用银行内部交易数据，卡组织对接作为 Phase 3 可选项 |
| **用户期望管理**（返现计算结果与银行实际结果不一致） | 🟡 中 | 明确展示"预估"标识，注明"最终以银行账单为准" |
| **除外类目清单不完整** |🟡 中 | 建立用户反馈机制，持续更新除外类目清单 |
| **SimplyGo 交通费计入逻辑复杂**（不同银行规则不同） | 🟡 中 | 参考 DBS Live Fresh 的 SimplyGo 计入门槛逻辑，配置化处理 |

## 七、合规与监管考量

- 新加坡 MAS 要求银行披露收费细则，返现规则说明需符合透明披露要求
- 参考《银行服务收费基准清单》（MAS 2024年12月更新）确保文案合规
- 返现金额计算需留存交易日志，满足反洗钱（AML）审计要求
- 若支持跨境返现，需考虑 MAS 跨境支付监管要求（2026年1月更新）
